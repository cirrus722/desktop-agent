## 什么时候用
用户要验证改动，或者测试已经红了，需要先定位再修改。

## 步骤
1. 先看工作区里有没有 `pytest.ini`、`pyproject.toml`、`tests/` 或 `test_*.py`，确认测试入口。
2. 优先跑项目已有的最短命令：`python -m pytest -q`；没有 pytest 时跑 `test_*.py`。
3. 只读失败用例的 traceback，最多看 3 个；不要一次把全部输出倒进上下文。
4. 按「哪个用例 / 期望什么 / 实际什么 / 最可能的原因」四件事总结。

## 不要做什么
- 不要先改代码再找原因。
- 不要用 `-vv` 或把 80 行 traceback 原样复制回来。
- 不要因为一个用例失败就重写整个测试文件。

## 输出格式
- 通过：命令、通过数量、耗时。
- 失败：每个失败用例三行，分别写用例名、期望/实际、最可能原因。
- 没有测试：说明搜索过哪些入口，建议补最小测试，不要假装已通过。

## 什么时候该停
- 同一错误连续出现两次，停止盲目重试，先读实现和测试的前置条件。
- 测试命令本身不可用（依赖缺失、入口不存在）时，先报告环境问题。

## 怎么算做完了
- 测试命令退出码为 0，且输出里有明确的通过数量。
- 如果仍然失败，答案里包含失败用例、期望、实际和下一步定位动作。
